# 热替换与状态迁移

> 研究方向优先级 **1（最高）**。目标：**零停机**换代，且在途时间流不撕裂。

---

## 1. 问题分解

热替换要同时满足三件事，缺一不可：

| # | 要求 | 公理维度 | 失败表现 |
|---|---|---|---|
| R1 | 换代期间服务不中断 | 时间 | 请求 5xx |
| R2 | 在途请求全部完成或安全中断 | 时间 | **时间流撕裂**（响应丢失/半写） |
| R3 | 旧实例空间被彻底回收 | 空间 | 内存泄漏 / 悬垂指针 |

---

## 2. 核心机制：Generation + 原子切换 + Drain

### 2.1 三个关键构件

| 构件 | 作用 |
|---|---|
| `Generation(u64)` | 插件实例的**世代标识**。同一 `PluginId` 在换代期间存在两个 Generation（旧 + 新），事件永远只被路由到"当前世代" |
| `ArcSwap` 原子切换 | 注册表整体替换，读侧无锁；切换瞬间即完成"新事件进新实例" |
| `DrainCoordinator` | 在途计数器 + deadline 闸门；旧实例拒新后在途归零方可回收 |

### 2.2 时间线（顺序管道事务，8 步）

```
  t0                    t1              t2         t3            t4         t5
  │                     │               │          │             │          │
  ▼                     ▼               ▼          ▼             ▼          ▼
[validate] ─▶ [load(new,g+1)] ─▶ [snapshot/restore] ─▶ [start(new)] ─▶ [switch_gen 原子] ─▶ [drain(old,g)] ─▶ [destroy(old)]
                                                                            │                    │
                                                                    此后新事件只进 g+1      拒新 + 等在途归零
                                                                                                │
                                                                                       超时 ⇒ 强制推进 + Failed
   任一步失败 ⇒ rollback：switch_gen 回退 g，destroy(new)，标记 Failed
```

| 步 | 操作 | 失败处理 | 错误码 |
|---|---|---|---|
| 1 | `validate_manifest`（Schema + ApiVersion + 能力 + 环检测） | 中止，旧实例不受影响 | `K201/K202/K301/K204` |
| 2 | `domain.load(new)` → 分配 `Generation = g+1` | 中止 | `K203/K5xx` |
| 3 | 若 `migratable`：`snapshot(old) → checksum → restore(new)` | **中止并丢弃新实例**（旧实例仍 Running，服务未受影响） | 插件自定义 |
| 4 | `start(new)` | 中止 + `destroy(new)` | `K5xx` |
| 5 | `registry.compare_switch(id, expected=g, new=g+1)`（**CAS 原子**） | 仅当 `expected != current` 时失败（`GenerationMismatch`），说明已被并发替换 | — |
| 6 | `old → Draining → drain(timeout)` | 超时则强制推进并标记 `Failed` | `K401` |
| 7 | `destroy(old)` 回收空间 | 记录告警（潜在泄漏） | — |
| 8 | 广播 `kernel.plugin.hotswapped` | — | — |

**关键性质**：第 5 步之前，新实例的所有失败都不会影响线上服务（旧实例始终 `Running`）；第 5 步之后新实例已就绪，回滚成本仅为一次反向切换。

### 2.3 drain 协议

```rust
// 插件侧义务
async fn drain(&self, timeout: Duration) -> Result<()> {
    // 1. 停止接收新工作（内部置 draining 标志）
    // 2. 等待在途工作完成，或响应取消信号
    // 3. 超时前返回；内核侧另有 deadline 兜底
}

// 内核侧闸门（guard 必须在**调度器帧**，即 catch_unwind **之外**、且 `?` 之外）
let guard = drain_coordinator.acquire(gen)?;   // 若已 draining → Err(Draining) 直接拒新
let res   = domain.dispatch(handle, env).await;
drop(guard);                                    // 计数 -1
```

**guard 的三条硬约束**（违反任意一条都会导致 `await_drain` 永不归零 → 热替换死锁）：

1. **用 RAII，不要手写 `release`**——`let r = dispatch(...).await?;` 里的 `?` 会跳过后续的 `release()`；
2. **guard 落在调度器帧，不要落在插件 future 内部**——future 被取消（drop）或被 `catch_unwind` 包住时，其内部跨 `.await` 持有的 guard 何时释放是实现细节，不可依赖；
3. **`acquire` 时即快照 `gen`**——不得在 dispatch 途中重新查询当前世代（B5）。

| 参数 | 建议值 | 说明 |
|---|---|---|
| `drain_timeout` | 插件 `deadline` 的 1.5 倍，默认 30s | 由清单 `time.deadline` 推导 |
| 强制推进 | 超时后 `Supervisor` 直接 `destroy` | ADR-010：防热替换被长任务永久阻塞 |
| 可观测 | drain 期间发布 `kernel.plugin.draining{remaining}` 指标 | 便于运维判断 |

## 3. 状态迁移协议

### 3.1 两条路径

| 路径 | 条件 | 代价 |
|---|---|---|
| **可迁移** | 实现 `Migratable` 且 `format` 版本匹配 | 一次序列化 + 反序列化 |
| **丢弃 + 冷启动** | 未实现 `Migratable`，或 `restore` 失败 | 旧状态丢失，新实例从初始态开始 |

### 3.2 协议

```rust
pub struct Snapshot {
    pub plugin_id:  PluginId,
    pub generation: Generation,      // 来源世代
    pub format:     SnapshotFormat,  // 如 "bincode:1" / "json:1"
    pub payload:    Bytes,
    pub checksum:   u32,             // CRC32，防传输损坏
}
```

**流转**：`snapshot()` → 校验 `format`（不匹配则转"冷启动"路径）→ `transfer`（进程内为内存移动；进程域为 gRPC 字节流）→ `restore()` → 校验返回值。

**安全约束**：
- `restore` 失败 → 整个热替换 **rollback**（不留下半初始化实例）。
- 快照中的 `generation` 必须等于旧实例的 `from_gen`，防止串代。
- 快照 payload 视为**不可信输入**：`restore` 必须自行做边界校验（防止恶意插件借快照穿透）。

### 3.3 依赖方影响

若插件声明 `bus_publish = ["llm.*"]`，换代期间其**订阅者不受影响**——因为事件模型是"按事件类型路由"而非"按实例引用路由"，订阅者只在下一次路由时自然切换到新世代。

若**依赖方**被替换（如 `tool-registry` 换代），依赖它的 `llm-adapter` 通过软依赖（`kind = "soft"`）降级：收到 `kernel.plugin.hotswapped` 后重新解析依赖句柄，解析失败则进入降级模式并告警。

## 4. 回滚策略

| 阶段 | 回滚动作 |
|---|---|
| 步 1–4 失败 | `compare_switch` 未执行 → 仅 `destroy(new)`，旧实例毫发无损 |
| 步 5 之后、步 6–7 失败 | `compare_switch(id, expected=g+1, new=g)` 切回旧世代 → `destroy(new)`；**注意：旧实例此时可能已 `Destroying`，需区分"旧实例仍可用"与"旧实例已销毁"两种情形** |
| 步 6 强制推进 | 不回滚（旧实例已不可用），仅标记 `Failed` 并告警 |

**重要边界**：一旦旧实例进入 `Destroying` 且空间已回收，回滚**不再可能**。因此设计上把"不可逆点"推迟到步 6 完成之后——即：**只要旧实例还在 `Draining` 或 `Stopped`（空间未回收），回滚都成立**。

**A4 · 回滚必须走 CAS（强制）**：上表的 `compare_switch` **不可**退化成 `switch_generation(id, g)`。理由：

- 同一 `PluginId` 的两次热替换若（因实现缺陷）并发发生，非 CAS 的切换会把世代切到一个**第三方世代**，造成世代错乱；
- 回滚时 `expected` 必须填 **`to_gen`（本次计划引入的世代）而非 `from_gen`**。若填错，`expected != current` 会直接返回 `GenerationMismatch`，把 bug 暴露在切换点而不是潜伏到后面；
- `GenerationMismatch` 的正确处理是**放弃本次回滚**并上报（说明状态已被他方推进），**不是**重试或强制覆盖。

**A4' · 世代快照而非世代查询**：热替换事务开始时把 `from_gen` 快照进 `HotSwapPlan`，事务内**禁止**再调 `generation(id)` 重新查询。所有写操作以该快照作为 CAS 的 `expected`。

## 5. 失败模式与反模式

| 反模式 | 后果 | 正解 |
|---|---|---|
| 原地改写注册表条目 | 读侧观察到半替换状态（空间撕裂） | `ArcSwap` 整体原子替换（ADR-012） |
| 先 destroy 旧实例再 load 新实例 | 换代窗口期服务中断（违反 R1） | 双世代共存，先起新后代旧 |
| 无 drain，直接 drop | 在途请求丢失（时间流撕裂） | `DrainCoordinator` + deadline |
| drain 无限等待 | 热替换被长任务永久阻塞（时间死锁） | 超时强制推进（ADR-010） |
| 快照不做 checksum / 不校验来源世代 | 串代、数据损坏 | `checksum` + `generation` 双重校验 |
| 跨 FFI 边界 panic unwind | UB | panic 边界在域内消化 |
| 热替换期间允许另一个热替换并发 | 世代错乱 | 同一 `PluginId` 的热替换加**互斥锁**（串行化）+ `compare_switch` CAS 兜底（A4） |
| 回滚用非 CAS 的 `switch_generation(id, g)` | 切到第三方世代 | `compare_switch(id, expected=to_gen, new=from_gen)`（A4） |
| drain 期间 in-flight 任务往满泳道 `publish` 且策略为 `Block` | 循环等待：计数永不归零 → 必超时 `K401` | `Draining` 世代豁免 `Block`，退化为 `Reject`（B4） |
| panic 捕获后仅 `return Err(K501)`，插件继续接客 | 状态污染的插件持续服务（静默数据损坏） | catch 分支唯一动作 = `transition(id, Failed)` + 卸载（B2） |
| 用 `broadcast` 投递生命周期状态 | 慢消费者 `Lagged` 静默丢事件 → 依赖方永久降级 | 状态类用 `watch` + "先订阅再读当前值" reconcile（B1） |

## 6. 验证（对应 P/Q/I）

| 维度 | 用例 |
|---|---|
| **Q3** | 热替换后发布 1000 条事件，断言全部由 `to_gen` 处理 |
| **Q4** | 旧实例注入 10 个耗时 2s 的任务后触发热替换，断言 10 个任务全部完成（无丢失，`await_drain` 在超时前归零） |
| **Q4'** | 注入耗时超过 `drain_timeout` 的任务，断言超时被强制推进、事件记录 `K401`、内核存活 |
| **Q5** | 新实例 `start()` 中 panic，断言旧实例仍 `Running` 且服务未中断 |
| **I1** | 连续 100 次热替换后，断言未配对的 `init/destroy` 计数为 0（无泄漏） |
| **I3** | 用 v0.1.0 契约的插件在当前内核上热替换成功 |
| **I5** | 并发同一 `PluginId` 的两次热替换，断言串行执行且最终世代唯一 |

## 7. 实施顺序

| 步骤 | 交付 | 依赖 |
|---|---|---|
| S1 | `Generation` + `ArcSwap` 注册表 | Registry（A） |
| S2 | `LifecycleState` + `DrainCoordinator` | LifecycleManager（B） |
| S3 | 热替换 8 步事务（先不做迁移，走冷启动路径） | S1 + S2 + 进程内域（D1） |
| S4 | 回滚逻辑与失败注入测试 | S3 |
| S5 | `Migratable` + 快照后端（M4 阶段） | Snapshot（H） |
| S6 | 进程域 / WASM 域下的热替换（跨进程 drain 与字节迁移） | D2 / D3 |
