# 插件依赖图与加载顺序

> 研究方向优先级 **2（多执行域）/ 3（依赖图）** 的交汇部分。解决"谁先起、谁先死、能不能成环"。

---

## 1. 为什么依赖图是内核职责

| 理由 | 说明 |
|---|---|
| **时间防乱序** | 装载顺序错了，插件会拿到未就绪的依赖句柄（悬垂引用）——这是时间维度的错误，必须由编排时间的内核拦截 |
| **规则防穿透** | 若由插件自行解析依赖，插件可绕过能力门控直接拿到任意依赖 |
| **空间防越界** | 卸载顺序错了，会先销毁仍被引用的实例，造成悬垂指针 |

**结论**：依赖声明在清单（`L1`），图结构与校验在内核（`domain/registry`），顺序执行在 `runtime`。

## 2. 依赖模型

```rust
pub struct Depend {
    pub on:     PluginId,
    pub range:  VersionRange,   // semver 约束，如 "^0.2"
    pub kind:   DependKind,
}

pub enum DependKind {
    Hard,   // 缺失或版本不满足 ⇒ 拒绝装载（K204 / K201）
    Soft,   // 缺失 ⇒ 降级运行 + 告警；后续装载时自动补挂
}
```

| 规则 | 说明 |
|---|---|
| `Hard` 依赖缺失 | 装载期直接 `Rejected`，**不进入 `Loaded`** |
| `Soft` 依赖缺失 | 正常装载，插件收到 `unavailable` 句柄；被依赖方后续装载时广播 `kernel.plugin.loaded`，依赖方重新解析 |
| 版本不满足 | 等同缺失（按 `kind` 分别处理） |
| 跨域依赖 | 允许：`in-process` 插件可依赖 `wasm` 插件，因跨插件通信一律走事件总线，与域无关 |

## 3. 环检测

```rust
// domain/registry/dependency.rs
pub fn detect_cycle(g: &DiGraph<PluginId, EdgeKind>) -> Option<Vec<PluginId>>;
pub fn topo_order(g: &DiGraph<PluginId, EdgeKind>) -> Result<Vec<PluginId>, CycleDetected>;
```

- 算法：**DFS 三色标记**（白=未访问，灰=在栈上，黑=已完成）；遇到灰色节点即成环，回溯输出环路径。
- 时机：**装载期 `validate` 阶段**（热替换第 1 步），在图变更前先"试加边再检测"，成环则拒绝，不留副作用。
- 复杂度：O(V + E)。
- 输出：成环时返回完整环路径 `A → B → C → A`，写入错误 `K204 CycleDetected(path)`。

**注意**：`Soft` 边同样参与环检测。软依赖不代表"顺序无关"——顺序仍是时间契约的一部分。

## 4. 加载与卸载顺序

### 4.1 加载（拓扑序）

```
topo_order(deps)  →  [tool-registry] → [llm-adapter] → [agent-orchestrator]
                      无依赖            依赖 tool        依赖 llm
```

每个插件内部仍走完整生命周期：`load → start`。**全部 `start` 成功后**才广播 `kernel.started`。

### 4.2 卸载（逆拓扑序）

```
reverse_topo_order(deps)  →  [agent-orchestrator] → [llm-adapter] → [tool-registry]
```

每个插件：`Draining → drain(timeout) → Stopped → Destroying`。**先停止消费者，再停止提供者**，避免请求打到已销毁的插件。

### 4.3 内核自举顺序（bootstrap）

```
core（无依赖，编译期即定）
  ↓
infrastructure（配置源 / 快照后端就绪）
  ↓
domain（注册表 / 状态机 / 门控 建空结构）
  ↓
runtime（总线 / 调度器 / 域表 / Subscriber 装配）
  ↓
Kernel::init 完成（空间就绪，时间流未启动）
  ↓
读取 kernel.toml 的 plugins.auto_load，按拓扑序装载并 start
  ↓
interfaces（CLI / HTTP Admin 开始接受外部时间事件）
```

## 5. 依赖解析的运行时行为

| 场景 | 行为 |
|---|---|
| 装载 A，其 `Hard` 依赖 B 未装载 | 拒绝 A（`K204`），并提示"需先装载 B" |
| 卸载 B，但 A（`Hard`）依赖 B | **拒绝卸载 B**（`K204`）；需先卸载 A |
| 卸载 B，但 A（`Soft`）依赖 B | 允许；先广播 `kernel.plugin.unloading`，A 进入降级模式，再卸载 B |
| B 热替换换代期间，A 依赖 B | A 无需变更——事件按 `PluginId` 路由而非实例；`compare_switch` 后 A 的下一次调用自然落到新世代 |
| B 崩溃进入 `Failed` | 广播 `kernel.plugin.failed`；`Hard` 依赖方按策略降级或一并停止；`Soft` 依赖方降级并告警 |
| 运行时补挂 `Soft` 依赖 | **依赖可用性状态经 `watch` 广播最新值**（不是一次性事件），依赖方调用 reconcile 重新解析句柄（B1） |

## 6. 与能力门控的交互

依赖解析**不绕过**能力门控：

```
A 依赖 B  ⟂  A 想调用 B
                  │
                  ▼
        CapabilityGate::check(A, Bus::Publish("tool.*"))
                  │
        未声明 ⇒ K301（依赖存在 ≠ 有权调用）
```

**原则**：依赖图解决的是**时间顺序**（谁先起），能力门控解决的是**空间权限**（能碰什么）。两者不可互相替代。

---

## 6.1 `Soft` 依赖补挂的实现纪律（B1 / B5）

**为什么这里最容易出错**：跨插件通信一律走事件总线、按 `PluginId` 路由，**不存在跨插件的强引用句柄**，因此理论上不会出现"新插件拿着旧插件的死引用"。但"依赖是否可用"是一个**状态**，而状态若用一次性事件投递，就会出现**漏窗口**：

```
A 查询 B 不可用 ────────────▶ A 进入降级
                    ▲
                    └── B 在此刻装载完成，loaded 事件已发出（A 尚未订阅）⇒ A 永久降级
```

**正解（顺序不可颠倒）**：

```rust
// 1. 先订阅（watch 会立刻给出当前值）
let mut rx = dep_registry.watch(dep_id).await;
// 2. 再 reconcile：用刚拿到的最新值做一次解析
reconcile(dep_id, rx.borrow_and_update().clone()).await;
// 3. 此后循环消费变更
while rx.changed().await.is_ok() {
    reconcile(dep_id, rx.borrow_and_update().clone()).await;
}
```

| 禁令 | 原因 |
|---|---|
| 用 `broadcast` 投递"依赖可用" | 慢消费者 `Lagged` 会静默丢弃，且新订阅者收不到历史事件 |
| 只注册回调、不同步读当前值 | 订阅与查询之间存在漏窗口（上图） |
| 解析结果里携带实例强引用 | 违反"插件间禁止直接内存互访"的空间契约；只可携带 `PluginId` + `Generation` |
| 解析时不校验 `Generation` | 会解析到正在退场的旧世代；必须 `expected == current` |

## 7. 验证（对应 P/Q/I）

| 维度 | 用例 |
|---|---|
| **Q7** | 构造 A→B→C→A 的循环依赖，断言装载返回 `K204` 且环路径完整 |
| **Q7'** | `Hard` 依赖缺失时装载被拒；`Soft` 依赖缺失时装载成功且进入降级 |
| **Q7''** | 卸载被 `Hard` 依赖的插件时被拒绝；被 `Soft` 依赖时允许且依赖方降级 |
| **I5** | 断言加载顺序 == 拓扑序，卸载顺序 == 逆拓扑序（记录事件序列比对） |
| **I1** | 依赖链整体卸载后，全部实例 `destroy` 计数配对为 0 |
| **I2** | 跨域依赖（in-process → wasm）可正常通信且不产生直接内存引用 |

## 8. 实施顺序

| 步骤 | 交付 |
|---|---|
| S1 | `Depend` / `DependKind` 类型 + 清单解析（`schema/plugin-manifest.schema.json`） |
| S2 | `DependencyGraph`（petgraph）+ `detect_cycle` / `topo_order` / `reverse_topo` |
| S3 | 装载期接入：试加边 → 环检测 → 拓扑序装载 |
| S4 | 卸载期接入：逆拓扑序 + `Hard` 依赖保护 |
| S5 | `Soft` 依赖的运行时补挂与降级 |
| S6 | 依赖失效（插件 `Failed`）的级联处理 |
