# 内核核心模块 · 递归四层设计

> 对每个核心模块执行"数据规范 → 数据存储 → 数据流转 → 数据接口"四层拆解，并显式标注 `init/start/stop/destroy` 生命周期钩子落点。
> 递归层级：第1层 = 内核模块（锚定项目本质）；第2层 = 子模块（必须锚定父本质）。

---

## A. Registry — 空间归属表（`domain/registry`）

**第1层 · 本质**：在"内核负责开辟与隔离插件空间"的时空约束下，本模块的本质是 **插件身份与其私有空间绑定关系的唯一权威账本，以及插件间依赖关系的有向图**。

| 四层 | 设计 |
|---|---|
| **数据规范** | `PluginId`（字符串 + 命名空间校验）、`Generation(u64)`、`PluginMeta{id, api_version, domain: DomainKind, capabilities: Vec<Capability>, depends_on: Vec<Depend>, time_semantics, deadline}`、`Registration{meta, state, generation, handle: DomainHandle, ctx: PluginContext}`、`Subscription{plugin_id, pattern, priority, filter}` |
| **数据存储** | 主索引 `ArcSwap<HashMap<PluginId, Arc<Registration>>>`（读多写少，换代整体替换）；路由索引 `ArcSwap<HashMap<EventType, Arc<Vec<Subscription>>>>`（按 priority 预排序）；插件包由 `infrastructure/plugin_store` 落盘 |
| **数据流转** | ① `register` 写入并增量重建受影响事件的路由；② `compare_switch(id, expected, new)` **CAS** 整体原子替换主索引（热替换原子性来源，A4）；③ `unregister` 按**逆拓扑序**移除；④ 装载前调用 `DependencyGraph::validate` |
| **数据接口** | `register/unregister/route/get/generation/compare_switch/list_by_state` |

**B5 · 读撕裂与世代快照（强制）**：主索引与路由索引是**两个独立的 `ArcSwap`**，`route()` 与 `get()` 是两次独立读，两次之间可能已经换代。故：

- `dispatch` 开始时**一次性快照** `(handle, generation)`，此后**全程禁止二次解析**（不得在 await 之后重新 `get(id)`，否则一次调用可能跨越两个世代）；
- 在途请求继续跑在**旧世代**上是**正确且期望**的行为（时间流不撕裂），任何"顺手刷新到最新世代"的实现都是 bug；
- 世代过滤必须显式写出 `expected == current`，不得依赖"当前上下文中取到的就是最新的"。
| **生命周期钩子** | `init`：建空主索引与路由索引（空间开辟）<br>`start`：无副作用（纯数据结构，无独立时间流）<br>`stop`：冻结写入（只接受路由读）<br>`destroy`：按逆拓扑序清空，逐个触发 `DomainHandle` 的 `Drop`（空间回收） |

### A1. DependencyGraph（第2层）

**本质**：在"注册表维护插件归属"的时空约束下，本子模块的本质是 **保证装载时间流顺序合法（无环）的有向图校验器**。

- 规范：`Depend{on: PluginId, kind: Hard | Soft, range: VersionRange}`；`Edge{from, to, kind}`
- 存储：`petgraph::DiGraph<PluginId, EdgeKind>`
- 流转：`add_edge` → `detect_cycle()`（DFS 三色标记）→ `topo_order()` / `reverse_topo()`；`Soft` 依赖缺失时降级（告警但不阻断），`Hard` 缺失直接拒绝
- 接口：`add_edge / remove_node / validate -> Result<(), CycleDetected> / order_for_load / order_for_unload`
- 钩子：`init` 建图 → `destroy` 清图（无独立时间流）

### A2. Router（第2层）

**本质**：在"注册表维护插件归属"的时空约束下，本子模块的本质是 **把一条事件时间流扇出到合法订阅者的静态索引**。

- 规范：`EventPattern`（支持 `llm.*` 前缀通配与精确匹配）；`Priority` 排序键
- 存储：`HashMap<EventType, Vec<Subscription>>`（预排序，避免热路径排序开销）
- 流转：`subscribe` / `unsubscribe` 增量重建；`match(event)` 返回按优先级排序的 `Arc<Vec<..>>`（零拷贝）
- 接口：`subscribe / unsubscribe / match`
- 钩子：随父模块 `init/destroy`

## B. LifecycleManager — 生命周期状态机（`domain/lifecycle`，`runtime` 驱动）

**第1层 · 本质**：在"内核编排插件的执行时间流"的时空约束下，本模块的本质是 **插件状态在合法迁移路径上的唯一仲裁者，尤其保证热替换时 in-flight 请求被安全 drain**。

| 四层 | 设计 |
|---|---|
| **数据规范** | `LifecycleState{Unloaded, Loading, Rejected, Loaded, Starting, Running, Draining, Stopped, Destroying, Failed}`；`Transition{from, to, at: Instant, reason}` |
| **数据存储** | 状态驻留 `Registration.state`（内存，随注册表 `ArcSwap` 一并原子替换）；迁移历史由 `infrastructure` 审计日志落盘（可选） |
| **数据流转** | 合法迁移图见下；迁移由 `application` 用例编排，`runtime` 执行域内实际调用；每次迁移广播 `kernel.plugin.lifecycle` 事件 |
| **数据接口** | `transition(id, to) -> Result<(), IllegalTransition>`、`state_of`、`history(id)`、`is_draining`、`drain_deadline` |
| **生命周期钩子** | `init`：所有登记项置 `Unloaded`<br>`start`：订阅生命周期事件流<br>`stop`：触发全局 drain（逆拓扑序）<br>`destroy`：逆序销毁并清空历史 |

### 状态迁移图

```
                    ┌──────────────────────────────────────────┐
                    │                                          │
  Unloaded ──▶ Loading ──┬──▶ Loaded ──▶ Starting ──┬──▶ Running
                         │                          │            │
                         ▼                          ▼            ▼
                     Rejected                    Failed ◀──── Draining
                   (契约/环检测失败)              (panic/drain超时)  │
                                                                    ▼
                                       Unloaded ◀── Destroying ◀── Stopped
```

**强制规则**：任意状态可 → `Failed`；`Failed` 只能 → `Destroying`。`Running → Draining` 时置 `deadline`，超时由 `Supervisor` 强制推进（ADR-010）。

### B1. DrainCoordinator（第2层）

**本质**：在"生命周期状态机保证时间流不撕裂"的时空约束下，本子模块的本质是 **在途请求计数器 + 超时熔断的闸门**。

- 规范：`InFlight{plugin_id, generation, count: AtomicU32, deadline: Instant}`
- 存储：`HashMap<(PluginId, Generation), Arc<InFlight>>`
- 流转：`acquire`（计数 +1，若已在 draining 则直接返回 `Draining` 错误以拒新）→ `release`（-1，归零时唤醒等待者）→ `await_drain(timeout)`（超时返回 `K401` 并交 `Supervisor` 强制推进）
- 接口：`acquire / release / await_drain / inflight_count`
- 钩子：随父模块；`destroy` 时对所有未归零计数告警（潜在空间泄漏信号）

## C. Scheduler / EventBus — 时间编排（`runtime/scheduler`）

**第1层 · 本质**：在"内核编排插件的执行时间流"的时空约束下，本模块的本质是 **事件循环 Loop 的载体与分发器，负责优先级、并发度与背压**。

| 四层 | 设计 |
|---|---|
| **数据规范** | `Envelope{trace_id, span_id, event, target, priority, deadline, generation}`；`Priority{Critical, High, Normal, Low}`；`BackpressurePolicy{Reject, Block, DropOldest}` |
| **数据存储** | 4 条**有界** `mpsc` 泳道（容量见 `kernel.toml`）+ **状态类通道用 `watch`、事件类通道用 `broadcast`**（见 B1）；容量有界是背压的物理前提 |
| **数据流转** | `recv` 加权轮转取事件 → 开 span（注入 `trace_id`）→ `Registry::route` 取订阅者 → **一次性快照 `(handle, generation)`（B5）** → 逐个：`CapabilityGate::check` → `DrainCoordinator::acquire`（guard 落在**调度器帧**，`catch_unwind` **之外**、且 `?` 之外）→ `Semaphore` permit（`max_inflight`，在 `spawn` 前获取）→ 按 `TimeSemantics` 串行 / `tokio::spawn`（带 `CancellationToken`，句柄收进 `JoinSet`）→ `ExecutionDomain::dispatch` → 错误记录并上报 |

**B1 · 状态类信息用 `watch`，事件类信息用 `broadcast`（强制）**：`tokio::sync::broadcast` 的慢消费者会收到 `Lagged` 并被**静默丢弃**。而"生命周期状态""软依赖是否可用"属于**状态**（最新值语义），一旦丢一条 `kernel.plugin.loaded`，依赖方会**永久停在降级模式**——编译过、运行不报错、功能就是不对。故：

| 信息类别 | 通道 | 语义 | 示例 |
|---|---|---|---|
| **状态**（可重放、幂等） | `watch` | 最新值，订阅即得当前值 | 插件生命周期状态、软依赖可用性、配置 |
| **事件**（一次性、审计） | `broadcast` | 尽力投递，允许 `Lagged` | 审计日志、指标事件 |

依赖解析必须写成 **"先订阅 → 再立刻读当前状态" 的 reconcile 函数**（顺序不可颠倒，否则漏窗口），而**不是**"注册一个等事件的回调"。
| **数据接口** | `publish(Event, Priority) / subscribe(pattern) / dispatch(env) / set_backpressure(policy)` |
| **生命周期钩子** | `init`：建通道与泳道<br>`start`：`tokio::spawn(run(shutdown_token))` 启动主循环<br>`stop`：取消 token → 停止收新 → 等在途归零 → flush<br>`destroy`：关闭通道、`abort` 残留任务、回收句柄 |

### C1. PriorityLanes（第2层）

**本质**：在"调度器承载事件时间流"的时空约束下，本子模块的本质是 **在有限容量下按权重分配时间片、防止低优先级饿死的排队结构**。
- 规范 `Lane{priority, weight, capacity}`（默认权重 8:4:2:1）；存储：定长环形缓冲；流转：加权轮转 dequeue；接口 `enqueue / dequeue_weighted / watermark`

### C2. Backpressure（第2层）

**本质**：在"调度器承载事件时间流"的时空约束下，本子模块的本质是 **把时间流过载转化为可策略化规则的水位闸门**。
- 规范 `Watermark{used, cap, ratio}`；存储：每泳道原子计数；流转：超 90% 触发策略；接口 `on_full(policy) / current_watermark`

## D. ExecutionDomain — 多执行域（`runtime/domain`）

**第1层 · 本质**：在"内核强制校验插件契约与权限"的时空约束下，本模块的本质是 **L2 线协议在不同隔离强度宿主上的执行器集合——即时空规则的执行者**（ADR-009：属于内核，不是插件）。

| 四层 | 设计 |
|---|---|
| **数据规范** | `DomainKind{InProcess, Wasm, Process}`；`DomainHandle{kind, id, inner: DomainInner}`；`trait ExecutionDomain`（`kind/load/start/dispatch/drain/destroy`） |
| **数据存储** | `DomainTable: HashMap<DomainKind, Arc<dyn ExecutionDomain>>`；各域自持资源：`Arc<dyn Plugin>` / `wasmtime::Store` + 实例 / 子进程句柄 + gRPC channel |
| **数据流转** | `dispatch` 前：`ApiVersion` 匹配 + `CapabilityGate::check`；`dispatch` 中：域内执行，**panic 边界在域内消化**（禁止跨 FFI unwind）；`dispatch` 后：结果封装 `Option<Envelope>` 回传 |
| **数据接口** | `ExecutionDomain` trait 六方法；`DomainTable::get(kind)` |
| **生命周期钩子** | `init`：注册已启用的域适配器<br>`start`：进程域健康检查 / WASM 引擎预热<br>`stop`：按逆序对各域内所有句柄 `drain`<br>`destroy`：逆序 `destroy` 全部句柄并清空表 |

### D1. InProcessDomain（第2层）

**本质**：在"多执行域提供不同隔离强度"的时空约束下，本子模块的本质是 **同语言零开销快车道——以编译期类型换取调用性能，以 `catch_unwind` 换取错误隔离**。
- 规范：`Arc<dyn Plugin>`；存储：随 `Registration.handle`
- 流转：`dispatch` 包裹 `AssertUnwindSafe(...).catch_unwind()`（async 场景用 `FutureExt::catch_unwind`）；**捕获后的唯一动作是 `transition(id, Failed)` 并触发卸载**，不得仅 `return Err(K501)`（B2）
- 接口：实现 `ExecutionDomain`
- 钩子：`load` 构造实例 → `destroy(&self)` 幂等通知 → `Drop` 真正释放（A1）

### D2. WasmDomain（第2层）

**本质**：在"多执行域提供不同隔离强度"的时空约束下，本子模块的本质是 **以线性内存与组件模型实现内存级强隔离、同时保持近原生性能的跨语言通用道**。
- 规范：`kernel.wit` 组件接口；`fuel_limit` + `epoch_tick` + `host_timeout` 三重时间上限（B3）
- 存储：`wasmtime::Store`（每个插件独立 Store = 独立线性内存）⇒ **每插件同时仅 1 个 in-flight 调用**，故 `TimeSemantics` 强制 `Serial`（A3）
- 流转：实例化 → 装载期 wit 类型校验 + `semantics != "concurrent"` 校验（否则 `K202`）→ `dispatch` 传入序列化 payload → 所有 host call 包 `tokio::time::timeout` → trap 转 `K502` → fuel 耗尽 / epoch 中断转 `K402`
- 钩子：`load` 实例化组件 → `destroy` 丢弃 Store（整块线性内存回收）

### D3. ProcessDomain（第2层）

**本质**：在"多执行域提供不同隔离强度"的时空约束下，本子模块的本质是 **以 OS 进程边界换取语言无关性与崩溃自愈能力的通用道**（ADR-004：跨语言优先）。
- 规范：`kernel.proto`；`DeliveryGuarantee::AtLeastOnce` + 幂等键
- 存储：子进程句柄（`Child`）+ gRPC channel + 健康检查状态
- 流转：spawn → 握手协商 `ApiVersion` → gRPC 调用（metadata 携带 `trace_id`）→ 心跳检测 → 连接中断转 `K503` 并按策略重启
- 钩子：`load` spawn 并握手 → `drain` 发送 drain 指令并等在途 → `destroy` 优雅退出（SIGTERM → 超时 SIGKILL）

## E. CapabilityGate — 能力门控（`domain/capability`，`runtime` 执行）

**第1层 · 本质**：在"内核强制校验插件契约与权限"的时空约束下，本模块的本质是 **把"插件能碰哪些外部空间"从运行期约定提升为装载期可判定、调用期可拦截的显式规则**。

| 四层 | 设计 |
|---|---|
| **数据规范** | `Capability` 枚举：`Net:Outbound(host)`、`Fs:Read/Write(path)`、`Env:Read(key)`、`Kernel:Spawn`、`Kernel:Shutdown`、`Bus:Publish(ty)`、`Bus:Subscribe(ty)`、`Clock`、`Random`；策略 `Grant/Deny`；默认 **deny-by-default**（ADR-011） |
| **数据存储** | 声明来自插件清单（TOML），经 JSON Schema 校验后驻留 `HashMap<PluginId, Arc<CapabilitySet>>`；策略源可来自配置文件 |
| **数据流转** | 装载期：`Schema` 校验 → `ApiVersion` 兼容 → 能力合法性 → 依赖环检测（任一项失败即 `Rejected`）；调用期：`check` 命中 Deny 返回 `K301/K302` 并发出 `kernel.capability.denied` 审计事件 |
| **数据接口** | `validate_manifest(m) -> Result<()>`、`check(id, &cap) -> Result<()>`、`granted(id) -> Vec<Capability>` |
| **生命周期钩子** | `init`：加载策略 → `start`：订阅越界审计事件 → `stop`：冻结策略变更 → `destroy`：清空策略表 |

## F. HotSwap 用例（`application/hotswap`）

**第1层 · 本质**：在"内核支持不停机替换能力"的时空约束下，本模块的本质是 **一次跨模块的事务性编排：新版本上台与旧版本退场必须原子、可回滚、且不撕裂在途时间流**。

| 四层 | 设计 |
|---|---|
| **数据规范** | `HotSwapPlan{plugin_id, from_gen, to_gen, drain_timeout, rollback_on_failure}`；`HotSwapReport{steps: Vec<Step>, duration, drained: u32, rolled_back: bool}` |
| **数据存储** | 无自有存储；编排 `Registry` + `LifecycleManager` + `ExecutionDomain` + `Snapshot` 四者状态 |
| **数据流转** | 顺序管道事务，8 步（详见 `06`）：validate → load → [snapshot→transfer→restore] → start → `compare_switch`（CAS，A4） → drain → destroy → 失败 rollback |
| **数据接口** | `hotswap(plan) -> Result<HotSwapReport>`；由 `interfaces`（CLI `kernelctl hotswap` / HTTP `POST /plugins/{id}/hotswap`）触发 |
| **生命周期钩子** | `init`：注入依赖 → `start`：订阅热替换请求事件 → `stop`：拒绝新计划、等在途计划完成 → `destroy`：释放编排资源 |

## G. Observability — 可观测性（`core` 门面 + `runtime/observability`）

**第1层 · 本质**：在"内核承担跨插件 trace 串联"的时空约束下，本模块的本质是 **为所有时间流分配统一的因果标识（`trace_id`），使跨插件、跨执行域的调用链可被完整重建**。

| 四层 | 设计 |
|---|---|
| **数据规范** | `TraceId`（ULID，时间有序）、`SpanId`、`SpanKind{Internal, Plugin, Domain, Bus}`、`LogLevel`、`MetricKey` |
| **数据存储** | `tracing` Subscriber + span 栈（内存）；导出由 `infrastructure/metrics_export`（OTLP / 文件 / stdout） |
| **数据流转** | 事件入调度器即开 span → `trace_id` 随 `Envelope` 透传（进程域经 gRPC metadata、WASM 域经组件调用参数、进程内域经 span 上下文）→ 插件回传后闭 span |
| **数据接口** | `span_for(trace_id) -> Span`、`inject(env)`、`record_error(plugin, err)`、`export()` |
| **生命周期钩子** | `init`：装配 Subscriber → `start`：启动导出任务 → `stop`：flush 缓冲（防止尾部数据丢失） → `destroy`：关闭导出器 |

> **易漏项**：插件自打日志无法完成链路追踪，故此项必须留在内核（ADR-008）。

## H. Snapshot / Migration（`domain/snapshot` + `infrastructure`）

**第1层 · 本质**：在"热替换时旧插件状态可丢弃或可快照迁移"的时空约束下，本模块的本质是 **插件私有空间在换代之间的序列化与移交协议**。

| 四层 | 设计 |
|---|---|
| **数据规范** | `trait Migratable{snapshot() -> Result<Snapshot>; restore(Snapshot) -> Result<()>}`；`Snapshot{plugin_id, generation, format: SnapshotFormat, payload: Bytes, checksum}` |
| **数据存储** | 内存态由插件自持；落盘 / 上传由 `infrastructure/snapshot_store` |
| **数据流转** | `snapshot → 校验 format 版本 + checksum → transfer → restore`；未实现 `Migratable` 的插件走"丢弃 + 冷启动"路径；`restore` 失败即触发 rollback |
| **数据接口** | `snapshot(id) / restore(id, snap) / is_migratable(id) / discard(id)` |
| **生命周期钩子** | `init`：注册快照后端 → `start`：无 → `stop`：拒收快照请求 → `destroy`：清理临时快照文件（防空间泄漏） |

## 生命周期钩子总表（落点一览）

| 模块 | `init` | `start` | `stop` | `destroy` |
|---|---|---|---|---|
| Registry | 建空索引 | — | 冻结写入 | 逆拓扑序清空 + Drop |
| LifecycleManager | 置 `Unloaded` | 订阅生命周期事件 | 触发全局 drain | 逆序销毁 |
| Scheduler/Bus | 建有界泳道 | spawn 主循环 | 取消 token + drain | 关通道 + abort 任务 |
| ExecutionDomain | 注册域适配器 | 健康检查 / 引擎预热 | 全域 drain | 逆序 destroy 句柄 |
| CapabilityGate | 加载策略 | 订阅审计事件 | 冻结策略 | 清空策略表 |
| HotSwap | 注入依赖 | 订阅替换请求 | 拒新 + 等在途 | 释放编排资源 |
| Observability | 装 Subscriber | 启动导出任务 | flush 缓冲 | 关闭导出器 |
| Snapshot | 注册后端 | — | 拒收请求 | 清理临时快照 |

**闭环校验（不变量 I1）**：测试收尾断言"未配对的 `init`/`destroy` 计数 == 0"。

由于 A1 把句柄统一为 `Arc<dyn Plugin>`、把真正的释放交给 `Drop`，I1 的**物理判据**升级为：

- 每个已卸载插件的 `Arc::strong_count(handle) == 1`（注册表已移除、调度器已快照释放、无 `JoinHandle` 残留）；
- `DrainCoordinator` 中所有 `(PluginId, Generation)` 的 `inflight_count == 0`；
- `destroy` 调用次数 ≥ 1 且**幂等**（重复调用不改变状态）。
